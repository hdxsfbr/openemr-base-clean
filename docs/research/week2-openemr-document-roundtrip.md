# OpenEMR document storage and derived-resource round trips

Research for [Research OpenEMR document storage and derived-resource round trips](https://labs.gauntletai.com/andrebatista/andrebatista-openemr-base-clean/-/issues/3), 2026-09-21.

## Decision-relevant gist

OpenEMR has a supported patient-document upload/read round trip and read projections through FHIR `DocumentReference`/`Binary`, but the inspected system has no supported end-to-end operation that also persists extracted lab or intake facts with page/field provenance and retry-safe deduplication. The later design decision therefore has to choose the clinical representation and provenance/idempotency contract; it cannot treat the existing document hash, generated FHIR Provenance, or the Week 1 `actions/` prose as that contract.

## Baseline and scope

The repository was imported from OpenEMR master and identifies its core as **8.2.0-dev**; the source files sampled for this research are byte-identical to official OpenEMR commit [`7061f77d`](https://github.com/openemr/openemr/tree/7061f77d4161da5b23d0cd1e6255628eaed69ac6). The demo deployment is instead pinned to OpenEMR **8.1.1**, and the project already records one compatibility failure caused by that drift. Findings below describe the repository unless explicitly labeled as an HL7 capability; they are not evidence that the 8.1.1 image has the same interfaces. [Repository version](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/version.php#L18-L25); [pinned deployment image](https://labs.gauntletai.com/andrebatista/andrebatista-openemr-base-clean/-/blob/9730f3543dc2cd5d787c6182ab2b2fe607845ee3/infra/image/openemr.Dockerfile#L1-11); [recorded drift](https://labs.gauntletai.com/andrebatista/andrebatista-openemr-base-clean/-/blob/9730f3543dc2cd5d787c6182ab2b2fe607845ee3/ARCHITECTURE.md#L1355-1363).

This note establishes available storage, mappings, and constraints. It does **not** choose whether extracted facts should become laboratory results, general observations, questionnaire responses, or a separate review artifact.

## What can round-trip today

### Uploaded source documents

The standard API exposes `POST /api/patient/:pid/document`, guarded by the `patients/docs` write-or-add-only ACL, plus category-scoped listing and patient/document download routes. The upload takes multipart content, a category path, and an optional encounter id. `DocumentService::insertAtPath()` applies the configured secure-upload file check, requires an existing category and non-empty bytes, then calls the native `Document::createDocument()` service. The controller returns only a success boolean, not the created id, UUID, or hash, so a caller cannot obtain a stable source identity from the create response and must rediscover it through a later list/search. [Routes and ACLs](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/apis/routes/_rest_routes_standard.inc.php#L496-L515); [controller contract and response](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/src/RestControllers/DocumentRestController.php#L74-L124); [service validation](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/src/Services/DocumentService.php#L124-L176).

The native document object stores content in the configured encrypted filesystem, CouchDB, or an event-provided remote store. On success it assigns a document UUID, patient `foreign_id`, owner, MIME type, size, SHA3-512 content hash, optional encounter id, and category relationship. Its schema also has logical document date, revision, page count, issue link, deletion state, and generic foreign-record reference fields. [Storage and persisted metadata](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/library/classes/Document.class.php#L941-L1127); [`documents` schema](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/sql/database.sql#L1387-L1432); [category ACL and coding fields](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/sql/database.sql#L283-L335).

Read-back is supported in two shapes:

- The standard service lists `id`, name, MIME type, logical date, and stored hash within an exact patient/category pair; file retrieval also predicates on both document id and patient id. [Standard list and retrieval](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/src/Services/DocumentService.php#L96-L176).
- FHIR search projects patient documents as `DocumentReference` with document UUID, patient subject, category, author/custodian, status, optional encounter context, and an attachment URL to `Binary/{document UUID}`. The attachment mapping omits size and hash. That omission cannot be repaired by copying the native hash directly: FHIR R4 defines `Attachment.hash` as base64-encoded SHA-1, whereas OpenEMR stores a hex SHA3-512 digest. Binary retrieval rejects missing/deleted/expired documents and checks both patient ownership for patient-context tokens and category ACL access. Its response body is the native document bytes with their MIME type rather than a FHIR `Binary` JSON resource, so generic-client interoperability should be tested. [FHIR document mapping](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/src/Services/FHIR/DocumentReference/FhirPatientDocumentReferenceService.php#L132-L233); [attachment mapping](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/src/Services/FHIR/DocumentReference/Trait/FhirDocumentReferenceTrait.php#L106-L130); [FHIR R4 attachment hash](https://hl7.org/fhir/R4/datatypes-definitions.html#Attachment.hash); [Binary authorization and response](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/src/RestControllers/FHIR/FhirDocumentRestController.php#L83-L143).

This is a **read projection**, not a FHIR document-ingestion API. The inspected FHIR route table has `GET DocumentReference`, `GET Binary`, and `POST DocumentReference/$docref`; `$docref` generates or returns a CCD and does not accept an uploaded `DocumentReference`. OpenEMR's server scope list exposes read access for `DocumentReference`, `Binary`, `Observation`, `DiagnosticReport`, `QuestionnaireResponse`, and `Provenance`, but its FHIR write list contains only Patient, Practitioner, and Organization. The standard API separately advertises `user/document.crs`. [FHIR routes](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/apis/routes/_rest_routes_fhir_r4_us_core_3_1_0.inc.php#L247-L295); [FHIR server scope lists](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/src/Common/Auth/OpenIDConnect/Entities/ServerScopeListEntity.php#L72-L130); [standard document scope](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/src/RestControllers/OpenApi/OpenApiDefinitions.php#L129-L149).

### Laboratory facts

OpenEMR's native laboratory path is `procedure_order` → `procedure_report` → `procedure_result`. A result can carry code, text, date, value, units, range, abnormal flag, comments, correction/status, UUID, and a `document_id` reference to the source document. `ProcedureService` reads that relationship and includes the document id in its result projection. [Result schema](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/sql/database.sql#L10489-L10513); [service joins](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/src/Services/ProcedureService.php#L202-L271); [hydrated result](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/src/Services/ProcedureService.php#L430-L465).

The public surfaces inspected are read-only for these records: the standard procedure controller/routes provide GET/search, and the FHIR Observation routes provide GET/search. The laboratory FHIR mapper reads procedure results into Observation but does not emit the available `document_id` as `Observation.derivedFrom`. Therefore the native table can link a result to a whole document, but the current FHIR round trip loses even that link. [Standard procedure controller](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/src/RestControllers/ProcedureRestController.php#L29-L102); [FHIR Observation routes](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/apis/routes/_rest_routes_fhir_r4_us_core_3_1_0.inc.php#L493-L502); [laboratory mapper](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/src/Services/FHIR/Observation/FhirObservationLaboratoryService.php#L128-L206).

OpenEMR also has an internal `ObservationService::saveObservation()` for encounter-form observations. It can represent categories including `laboratory` and `survey`, and those records are readable through the FHIR Observation mapper. The save service requires raw patient, encounter, user, code, description, and date fields and performs no route-level authorization itself; it is an internal persistence primitive, not evidence of an authorized ingestion endpoint. [Save and validation contract](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/src/Services/ObservationService.php#L590-L702); [FHIR categories and read mapper](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/src/Services/FHIR/Observation/FhirObservationObservationFormService.php#L31-L78).

### Intake facts

`QuestionnaireResponseService::saveQuestionnaireResponse()` can persist a complete FHIR Questionnaire and QuestionnaireResponse JSON pair, bind it to patient and optional encounter, record creator/updater, and version later saves. The FHIR search mapper can read it back. However, core's FHIR controller exposes only GET/list and GET/one and explicitly says creation still depends on a private assessment module. The mapper also records that OpenEMR has no current link from a PDF survey to populated answers. [Internal save path](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/src/Services/QuestionnaireResponseService.php#L348-L533); [read-only controller and create TODO](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/src/RestControllers/FHIR/FhirQuestionnaireResponseRestController.php#L50-L215); [missing PDF-answer link](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/src/Services/FHIR/QuestionnaireResponse/FhirQuestionnaireResponseFormService.php#L198-L228).

FHIR provides appropriate vocabulary but not an OpenEMR implementation choice: `QuestionnaireResponse` distinguishes subject, recorder/author, answer source, encounter, status, and item-level answers; `Observation` represents atomic facts and permits `derivedFrom` references to `DocumentReference` or `QuestionnaireResponse`; `DiagnosticReport.result` groups atomic Observations for a report. [HL7 R4 QuestionnaireResponse](https://www.hl7.org/fhir/R4/questionnaireresponse.html); [HL7 R4 Observation](https://hl7.org/fhir/R4/observation.html); [HL7 R4 DiagnosticReport](https://hl7.org/fhir/R4/diagnosticreport.html).

## Provenance is not page/field provenance

FHIR separates the provenance of a document from the provenance of the `DocumentReference` that indexes it. FHIR `Provenance` can identify generated targets, the activity and agents involved, and source/derivation entities; that is enough vocabulary to say an Observation was derived from a document. It does not by itself define PDF page coordinates, OCR spans, form field rectangles, or the extraction model/version. Those details need a constrained extension or an application-owned provenance record linked to the FHIR/native record. [HL7 R4 DocumentReference provenance distinction](https://hl7.org/fhir/R4/documentreference.html); [HL7 R4 Provenance model](https://hl7.org/fhir/R4/provenance.html).

The current OpenEMR projections do less. `documents.pages` exists in the schema, but upload does not populate it, the standard listing does not return it, and the FHIR attachment mapping exposes only content type, URL, title, and format. OpenEMR's generated FHIR Provenance is synthesized from a resource's id, last-updated value, author/performer, and primary organization; it supplies a target and agents but no source entity, extraction activity, page, field, or extractor version. [Document fields](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/sql/database.sql#L1391-L1424); [standard projection](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/src/Services/DocumentService.php#L96-L121); [generated Provenance](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/src/Services/FHIR/FhirProvenanceService.php#L91-L153).

The project has only a reserved `document:{uuid}:page:{n}` source-id shape. The current `SourceRef` is still a table/id object, no source registry exists, no `document_extract` verifier rule exists, and no `actions/` write implementation exists. These are planned seams, not working provenance or write controls. [Week 2 seam audit](https://labs.gauntletai.com/andrebatista/andrebatista-openemr-base-clean/-/blob/9730f3543dc2cd5d787c6182ab2b2fe607845ee3/docs/WEEK2_HANDOFF.md#L80-L87); [planned contract](https://labs.gauntletai.com/andrebatista/andrebatista-openemr-base-clean/-/blob/9730f3543dc2cd5d787c6182ab2b2fe607845ee3/ARCHITECTURE.md#L482-L496).

Consequently, any later claim of field-level traceability must be able to resolve at least: immutable source document UUID and content fingerprint; page and field/span/region locator; extracted value as reviewed; extractor and contract version; extraction time and actor; and the exact resulting OpenEMR record identity. Confidence alone is not provenance, and a whole-document `document_id` cannot prove which page or field supports a displayed fact.

## Duplicate prevention and retry behavior

Document upload computes SHA3-512 and stores it, but neither the schema nor `insertAtPath()` makes the hash unique or checks it before creating a new UUID and file. The hash supports integrity checking; it is not an idempotency key. Retrying the same POST can therefore create another document record. [Hash creation and unconditional persist](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/library/classes/Document.class.php#L1109-L1127); [non-unique schema indexes](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/sql/database.sql#L1423-L1431).

The extracted-fact services likewise do not expose a client idempotency contract. Questionnaire response save treats a known response id as an update and otherwise inserts, while observation save updates by internal id plus patient/encounter or inserts without a client key. Neither is an atomic "create this extraction once" API. [Questionnaire create/update selection](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/src/Services/QuestionnaireResponseService.php#L419-L533); [observation update/insert](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/src/Services/ObservationService.php#L500-L577).

FHIR R4 defines conditional create with `If-None-Exist` and gives a lab identifier as its duplicate-prevention example, but servers need not implement it. The inspected OpenEMR routes do not expose create for DocumentReference, Observation, or QuestionnaireResponse, so the standard does not supply idempotency here. [HL7 R4 conditional create](https://hl7.org/fhir/R4/http.html#ccreate).

A later write contract must therefore specify, before implementation, the uniqueness scope, persistent idempotency key, behavior after partial failure, atomic relationship between source and derived rows, repeat/re-extraction semantics, and what counts as the same fact. Hash equality alone is insufficient because identical bytes may be intentionally filed twice, while a reprocessed document may produce a corrected fact under a new extraction version.

## Authorization and audit constraints

Authorization is enforced at the route/boundary, not by the low-level services. The standard document route checks OAuth scope plus `patients/docs` ACL and standard download constrains retrieval by patient id, while the service accepts a raw pid. The FHIR path additionally calls the document category's `can_access` check and, for patient-context tokens, binds search/download to the token patient. User-context reads remain as broad as the user's OpenEMR role. The standard and FHIR surfaces are therefore not authorization-equivalent, and both are weaker than this project's chart-bound policy, which additionally rechecks live session, conversation/site/user/patient binding, active chart, section ACL, squad, and break-glass state on every clinical boundary. [Standard route checks](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/apis/routes/_rest_routes_standard.inc.php#L496-L515); [standard patient-scoped retrieval](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/src/Services/DocumentService.php#L162-L176); [FHIR category and patient checks](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/src/RestControllers/FHIR/FhirDocumentRestController.php#L83-L143); [project boundary policy](https://labs.gauntletai.com/andrebatista/andrebatista-openemr-base-clean/-/blob/9730f3543dc2cd5d787c6182ab2b2fe607845ee3/docs/adr/0002-patient-scope-authorization.md#L41-L64).

OpenEMR records bearer-token success/failure and can audit external API requests at termination. API response logging is configuration-dependent, skips local API calls, and can include JSON response bodies; binary bodies are deliberately excluded by that listener. However, the FHIR document downloader itself places the full decrypted document bytes in a debug log context. That is an immediate PHI/logging hazard if debug output is enabled and needs runtime verification and mitigation before this path is used. None of these facilities establishes an action-specific audit record tying a source document, idempotency decision, extraction version, derived record ids, reviewer, and correlation id together. [Token audit](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/src/RestControllers/Authorization/BearerTokenAuthorizationStrategy.php#L284-L322); [API response audit behavior](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/src/RestControllers/Subscriber/ApiResponseLoggerListener.php#L39-L123); [decrypted-byte debug context](https://github.com/openemr/openemr/blob/7061f77d4161da5b23d0cd1e6255628eaed69ac6/src/Services/FHIR/Document/BaseDocumentDownloader.php#L53-L72).

For this repository, a clinical write is still forbidden until an explicit architecture decision authorizes it. The described `actions/` class, write-level ACL, action idempotency key, provenance fields, and dedicated audit event are design intent only. The agent service must never receive database credentials or write OpenEMR tables directly. [Planned action boundary](https://labs.gauntletai.com/andrebatista/andrebatista-openemr-base-clean/-/blob/9730f3543dc2cd5d787c6182ab2b2fe607845ee3/ARCHITECTURE.md#L334-L342); [accepted integration boundary](https://labs.gauntletai.com/andrebatista/andrebatista-openemr-base-clean/-/blob/9730f3543dc2cd5d787c6182ab2b2fe607845ee3/docs/adr/0003-integration-point-module-gateway.md#L192-L232).

## Questions the design ticket must still decide

The source evidence narrows, but does not answer, these decisions:

1. Which OpenEMR record is authoritative for each reviewed extraction class: native procedure result, encounter-form Observation, QuestionnaireResponse, or a separate non-clinical review record?
2. Is a human approval required before any clinical record is created, and how are rejected, amended, corrected, and reprocessed extractions represented without overwriting history?
3. Where does field-level provenance live, and how does every derived record resolve back to immutable document bytes plus page/field coordinates and extraction version?
4. What unique idempotency scope and transaction state machine make upload, extraction, review, and write retries safe after timeouts or crashes?
5. Which write ACL applies to each target type, what patient-context checks run immediately before commit, and what PHI-minimized audit event proves the attempt and outcome?
6. Which service contracts actually exist in the pinned 8.1.1 runtime, and what compatibility adapter or migration is acceptable if an 8.2-dev service is absent?

## Residual uncertainty

- This was source/specification research, not a live 8.1.1 upload/write/read test. Runtime configuration, site category trees, document storage backend, and installed forms can change behavior.
- The 8.2-dev tree contains internal save services that are absent from its public routes; their presence does not guarantee stability or backward compatibility.
- No upstream source found in the inspected paths establishes atomicity across a document row, file bytes, provenance, and multiple derived facts. A prototype against a disposable 8.1.1 database is needed before treating any proposed transaction boundary as proven.
- The standard FHIR model can express whole-resource derivation, but the exact interoperable representation for PDF page regions and field spans remains a profile/extension decision.
- Generic FHIR-client handling of OpenEMR's native-byte `Binary` response, and the operational reach of the decrypted-byte debug log, were not tested against the pinned runtime.
