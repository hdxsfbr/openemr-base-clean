# M4 resource baseline: idle, 10-user, and 50-user levels

Companion to `load-test-2026-09-18.md` — container CPU/memory and host
resource data from `docs/audit/scripts/droplet-stats.sh`, sampled every 5 s
over SSH against the live Droplet `137.184.4.22` (`s-2vcpu-4gb`, 2 vCPU /
4 GiB) throughout each window. Raw CSVs and `/metrics` snapshots:
`evals/load/results/droplet-stats-*.csv`. CPU percentages are Docker's
normalized figure, where 100% = one full vCPU core saturated.

## Reading this

**Memory was never the constraint.** Host memory available never dropped
below 2,389 MiB of 3,916 MiB total (the low-water mark, at 50 users under
`--fault model`) — over 60% free at the worst observed point. `ADR-0001`
names the 4 vCPU / 8 GiB size as "the first fallback if measurement shows
memory pressure"; this measurement shows no memory pressure at all.

**CPU is the constraint, and it saturates well before 50 users.** At 50
users, both `openemr` and `database` independently peak at or above 100% —
each one alone using more than the Droplet's two vCPU cores can give it,
before accounting for the other container or the host's own overhead. The
`load1` peak of ~24 on a 2-core host (fault run) means the run queue was
roughly 12x deeper than the box could actually execute at once. `agent` CPU
never exceeded 54% peak / 12% mean at any level, including under real model
load — the bottleneck is not in the agent service.

**This confirms `load-test-2026-09-18.md`'s conclusion independently**, from
resource data rather than from latency numbers: OpenEMR's Apache/PHP layer
and MariaDB are what saturates, not the copilot agent or the model provider.
