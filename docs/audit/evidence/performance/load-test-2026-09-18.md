## The `--fault model` control isolates the bottleneck to OpenEMR, not the agent or the model

`--fault model` makes zero real model calls (`plan` and `narrate` both
short-circuit on the fault flag — `agent/app/graph/nodes.py:175,192-193`) and
spent $0. Despite that, level 50 still produced:

- Chart-open p95 **46.15 s** — nearly identical to the real run's 46.3 s.
  Chart-open is a pure OpenEMR/Apache request; the agent is not involved at
  all in that measurement.
- **253 of 259 tool-gateway calls (97.7%) unavailable** (78 `http_5xx`, 175
  `timeout`) — nearly the same magnitude as the real run's 90% (277/309).
  Every tool call is `POST http://openemr:80/.../gateway/tools.php`
  (`agent/app/settings.py:14`, `agent/app/gateway_client.py:44`) — the same
  Apache/PHP process pool inside the `openemr` container that serves every
  browser page, per `tools.php:21`'s `require_once .../globals.php`.
- 17 of 50 VUs still dropped out early (chart_open=4, login=3, session=3,
  start=2, ticket=5) — almost the same dropout profile as the real run's 19.

One asymmetry to note when reading this control: `classify` routes a first
turn (`uc01_first`) straight to `retrieve`, which calls all six OpenEMR tools
unconditionally regardless of the fault flag (`agent/app/graph/nodes.py:106,144-145`).
A follow-up turn instead routes through `plan` first, which short-circuits
immediately under `--fault model` *without ever calling retrieve*
(`nodes.py:175-176`). So this control run under-counts real tool-gateway
load from follow-up turns — the real run's numbers are the more complete
picture of tool-gateway load, and the fault run's near-identical chart-open
and tool-failure magnitudes are the more conservative (i.e. still damning)
comparison point.

**Conclusion: the bottleneck is OpenEMR's Apache/PHP and MariaDB layer, not
the agent service or the model.** See `baseline-2026-09-18.md` for the
container-level CPU/memory evidence that confirms this directly (`openemr`
and `database` containers both saturating a full core each on a 2-vCPU
Droplet; `agent` CPU never exceeded ~54% peak).

## How the driver works

Each virtual user (VU) is one `httpx.AsyncClient` — a real async HTTP client
replaying the exact request sequence a browser panel session makes (login,
chart-open, CSRF, start conversation, ticket, turn, ticket, follow-up turn,
ticket, history) — with no browser, no JS execution, no rendering. N VUs run
as N concurrent asyncio tasks in one Python process, not N separate
processes or browser tabs. It hits both layers a real user would: OpenEMR's
own PHP pages (login, chart-open) and the agent's HTTP API
(`/copilot-api/v1/conversations/<id>/turns`) — see `evals/load/run_load.py`'s
module docstring for the full request table. Because it is HTTP-level, it is
a lower bound on real-world latency, not an upper bound: a real browser under
the same concurrent load would see at least this much latency, plausibly more.
